## 1. 배경

### 1.1 바이브코딩이란

Andrej Karpathy가 2025년 2월 제안한 개발 방식. AI에게 자연어로 원하는 것을 설명하고 코드를 생성하게 한 뒤, 코드를 한 줄씩 읽는 대신 동작 여부로 평가한다. 2025년 Collins Dictionary 올해의 단어로 선정.

### 1.2 바이브코딩의 성장

- 개인 프로토타이핑에서 팀 개발로 확산
- Cursor, Claude Code, Copilot 등 도구 생태계 성숙
- 비개발자(PM, 디자이너, 마케터)의 코드 생성 참여 증가
- Karpathy 본인이 2026년 초 "Agentic Engineering"으로 진화 선언

### 1.3 표준화 부재의 문제

바이브코딩의 핵심 약점은 **재현 불가능성**이다.

```
같은 요청, 같은 도구, 다른 사람, 다른 시간
→ 다른 품질, 다른 구조, 다른 결과

개인이 쓸 때: 괜찮음 (본인이 판단)
팀이 쓸 때:  카오스 (기준이 없음)
```

구체적 문제:
- **품질 편차**: 팀원 A의 "DB 설계"와 팀원 B의 "DB 설계"가 완전히 다른 결과
- **노하우 소실**: 효과적인 프롬프트/방법론이 개인에게만 축적
- **검증 부재**: AI 산출물의 품질 기준이 없음
- **비용 비효율**: 같은 작업을 매번 처음부터 시행착오

---

## 2. 핵심 문제 정의

> **바이브코딩은 개인 도구에서 팀 도구로 전환되는 시점에 표준화가 필요하다.**

이것이 Vibe Flow가 해결하는 본질적 문제다.

---

## 3. 솔루션: 블록 기반 표준화

### 3.1 블록이란

블록(Block)은 **팀이 검증한 AI 작업 방식의 캡슐화**다.

```yaml
# 블록 = 파이프라인 UI 부품이 아님
# 블록 = 팀의 레시피

하나의 블록에 담기는 것:
  - 검증된 프롬프트 템플릿
  - 최적 모델 설정
  - 팀 컨벤션 (코딩 규칙, 네이밍 규칙 등)
  - 품질 게이트 (산출물 검증 기준)
  - 메타데이터 (카테고리, 난이도, 예상 비용)
```

### 3.2 블록이 해결하는 것

| 문제 | 블록의 해결 |
|------|-----------|
| 품질 편차 | 누가 써도 같은 프롬프트, 같은 기준으로 실행 |
| 노하우 소실 | 프롬프트/방법론이 블록에 영구 저장 |
| 검증 부재 | 품질 게이트가 자동 검증 |
| 비용 비효율 | 검증된 블록 재사용으로 시행착오 제거 |

### 3.3 블록은 파이프라인이 아니다

초기 설계에서 블록을 드래그&드롭 파이프라인의 부품으로 구상했으나,
비판적 분석을 통해 핵심 가치를 재정의했다:

```
❌ 블록 = 사용자가 조립하는 파이프라인 부품
   → "비개발자에게 파이프라인을 노출하지 마라"

✅ 블록 = 팀이 검증한 표준 작업 단위
   → 사용자는 블록의 존재조차 몰라도 됨
   → "해줘" 한마디면 뒤에서 블록이 실행됨
```

## 4. 두 종류의 사용자

### 4.1 Block Creator (블록 생성자)

- **누구**: 리드, 시니어, PM
- **몇 명**: 팀당 소수 (2-5명)
- **하는 일**: AI와 대화로 블록 생성/수정/관리
- **인터페이스**: 웹 UI (대시보드)
- **필요 역량**: 작업 도메인 전문성 (코딩 능력 불필요)

### 4.2 Block Consumer (블록 사용자)

- **누구**: 팀원 누구나
- **몇 명**: 팀 전체 (10-100명)
- **하는 일**: 자연어로 작업 요청
- **인터페이스**: Slack, 텔레그램, 디스코드, 음성, 웹챗
- **필요 역량**: 없음 (블록의 존재를 몰라도 됨)

### 4.3 사용자 분리의 의미

비판적 분석에서 "타겟 유저가 존재하지 않는다"는 지적이 있었다:

```
블록을 이해할 만큼 기술적 → 이미 Claude Code를 직접 씀
블록을 이해 못하는 비개발자 → 블록 UI를 줘도 못 씀
```

이 문제를 **사용자 분리**로 해결했다:
- Creator는 기술적이지만 블록을 "만드는" 것이지 "코딩하는" 것이 아님
- Consumer는 블록을 모름. 그냥 대화함. 표준화는 뒤에서 자동으로 적용됨

## 5. 핵심 원칙

### 5.1 표준은 하나, 채널은 여럿

```
어디서 말하든 (Slack, 텔레그램, 음성, 웹)
→ 같은 코어 엔진
→ 같은 블록이 실행됨
→ 같은 품질이 보장됨
```

### 5.2 오케스트레이션은 보이지 않는다

사용자에게 파이프라인, DAG, 모델 라우팅을 노출하지 않는다.
이 모든 것은 내부에서 자동으로 처리된다.

### 5.3 네이티브를 활용한다

Claude Code가 이미 제공하는 기능(Remote Control, Channels, 세션 관리, 보안)은
직접 구현하지 않고 네이티브로 활용한다.

### 5.4 만들 것만 만든다

Vibe Flow가 만드는 것:
- 블록 정의/저장/버전 관리
- 블록 매칭 엔진 (trigger_phrases 퍼지 매칭 + IntentClassifier 폴백)
- 실행 하네스 (컨텍스트 주입, 품질 게이트, 재시도)
- Creator 웹 UI

Vibe Flow가 만들지 않는 것:
- 채팅 봇 (Claude Code Channels 사용)
- 웹/모바일 접근 (Claude Code Remote Control 사용)
- 인증/보안 (Claude Code allowlist 사용)
- AI 실행 엔진 (Claude Code CLI 사용)
- 벡터 DB / 임베딩 인프라 (수십 개 블록에는 과잉, 필요 시 추후 도입)

### 5.5 블록의 범위

> 비판적 검토를 통해 블록의 적용 범위를 명확히 정의했다.

```
블록 대상 (팀당 5-15개의 핵심 반복 워크플로우):
  - DB 스키마 설계, API 설계, 코드 리뷰, 보안 점검
  - 품질 게이트(자동 검증 + 재시도)가 가치를 발휘하는 구조화된 산출물

블록 비대상 (일반 Claude Code로 처리):
  - 디버깅, 탐색, 리팩토링, 1회성 질문
  - 비구조적이고 맥락 의존적인 작업

블록의 유일한 고유 가치 = 품질 게이트
  - 프롬프트 표준화 → CLAUDE.md로 80% 해결 가능
  - 팀 컨벤션 → CLAUDE.md로 해결 가능
  - 품질 게이트 → CLAUDE.md로 불가능. 블록만의 고유 영역
```

## 6. 경쟁 포지셔닝

```
            개인용              팀용
           ─────────────────────────────
직접 코딩  │ Cursor            │ GitHub Copilot
           │ Claude Code       │ Enterprise
           │                   │
대화형     │ Lovable, Bolt     │ ← Vibe Flow
           │ v0, Replit Agent  │   (여기가 비어있음)
           ─────────────────────────────
```

Lovable/Bolt은 개인이 빠르게 프로토타입하는 도구.
Vibe Flow는 **팀이 일관된 품질로 AI를 활용하는 표준화 플랫폼**.

## 7. 한 줄 정의

> 팀원은 어디서든 대화만으로 그 표준을 실행하는 플랫폼.**
