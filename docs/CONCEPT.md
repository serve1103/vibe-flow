## 1. 배경

### 1.1 바이브코딩이란

Andrej Karpathy가 2025년 2월 제안한 개발 방식. AI에게 자연어로 원하는 것을 설명하고 코드를 생성하게 한 뒤, 코드를 한 줄씩 읽는 대신 동작 여부로 평가한다. 2025년 Collins Dictionary 올해의 단어로 선정.

### 1.2 바이브코딩의 성장

- 개인 프로토타이핑에서 팀 개발로 확산
- Cursor, Claude Code, Copilot 등 도구 생태계 성숙
- 비개발자(PM, 디자이너, 마케터)의 코드 생성 참여 증가
- Karpathy 본인이 2026년 초 "Agentic Engineering"으로 진화 선언

### 1.3 표준화 부재의 문제

바이브코딩의 핵심 약점은 **재현 불가능성**이다.

```
같은 요청, 같은 도구, 다른 사람, 다른 시간
→ 다른 품질, 다른 구조, 다른 결과

개인이 쓸 때: 괜찮음 (본인이 판단)
팀이 쓸 때:  카오스 (기준이 없음)
```

구체적 문제:
- **품질 편차**: 팀원 A의 "DB 설계"와 팀원 B의 "DB 설계"가 완전히 다른 결과
- **노하우 소실**: 효과적인 프롬프트/방법론이 개인에게만 축적
- **검증 부재**: AI 산출물의 품질 기준이 없음
- **비용 비효율**: 같은 작업을 매번 처음부터 시행착오

## 2. 핵심 문제 정의

> **바이브코딩은 개인 도구에서 팀 도구로 전환되는 시점에 표준화가 필요하다.**

이것이 Vibe Flow가 해결하는 본질적 문제다.

---

## 3. 솔루션: 블록 기반 표준화

### 3.1 블록이란

블록(Block)은 **개인의 AI 작업 방식을 캡슐화한 재사용 가능한 템플릿**이다.

```yaml
하나의 블록에 담기는 것:
  - 검증된 프롬프트 템플릿
  - 최적 모델 설정
  - 품질 게이트 (산출물 검증 기준)
  - 메타데이터 (카테고리, 난이도, 예상 비용)

소유 모델:
  - 기본: 개인 소유 (본인만 사용)
  - 선택: 팀에 공유 가능 (공유 시 팀원 누구나 사용)
```

### 3.2 파이프라인이 표준을 보장한다

블록은 개인 템플릿이지만, **품질 일관성은 고정 파이프라인이 보장**한다.

```
누가 어떤 블록을 쓰든, 반드시 거치는 고정 스테이지:

  요청 → 세션 기억 → 스마트 인터뷰 → 블록 매칭
       → 실행 → 품질 게이트 → 코드 리뷰 → 보안 검토 → 출력

  블록 = 개인의 작업 방식 (자유)
  파이프라인 = 팀의 품질 기준 (고정)
```

| 문제 | 해결 주체 |
|------|----------|
| 품질 편차 | 파이프라인 (코드 리뷰 + 보안 검토가 일관된 기준 적용) |
| 노하우 소실 | 블록 (프롬프트/방법론이 블록에 저장, 공유 선택 가능) |
| 검증 부재 | 파이프라인 + 블록 (고정 게이트 + 블록 내장 게이트) |
| 비용 비효율 | 블록 (검증된 블록 재사용으로 시행착오 제거) |

### 3.3 블록과 파이프라인의 관계

```
❌ 블록 = 팀 전체가 공유하는 표준 레시피
   → 블록 관리 오버헤드가 크고, 개인 자유도가 낮음

✅ 블록 = 개인의 작업 템플릿 (공유 선택 가능)
   + 파이프라인 = 팀의 고정 품질 기준
   → 개인은 자유롭게, 팀 품질은 파이프라인이 보장
```

## 4. 두 종류의 사용자

### 4.1 팀원 (블록 생성자이자 사용자)

- **누구**: 팀원 누구나
- **하는 일**: 자신의 블록 생성/수정 + 자연어로 작업 요청
- **인터페이스**: 웹 UI, 텔레그램, 디스코드
- **필요 역량**: 없음 (블록 없이도 파이프라인이 품질 보장)

> 기존 설계는 Creator(소수)/Consumer(다수)를 분리했으나,
> 실제로는 모든 팀원이 자기 블록을 만들 수 있고, 공유는 선택이다.

### 4.2 파이프라인 관리자

- **누구**: 리드, 시니어
- **몇 명**: 팀당 소수 (1-3명)
- **하는 일**: 고정 파이프라인 스테이지 설정 (코드 리뷰 기준, 보안 검토 규칙 등)
- **인터페이스**: 웹 UI (대시보드)
- **필요 역량**: 팀 품질 기준에 대한 이해

### 4.3 역할 정리

```
기존: Creator(소수) vs Consumer(다수) → 엄격한 분리
현재: 팀원(누구나 블록 생성+사용) + 관리자(파이프라인 설정)

이 모델이 "타겟 유저 부재" 문제를 해결한다:
  - 블록을 이해하는 기술적 사용자 → 자기 블록 만들어서 사용
  - 블록을 모르는 비개발자 → 블록 없이 요청해도 파이프라인이 품질 보장
  - 누군가의 좋은 블록 → 공유하면 팀 전체가 혜택
```

## 5. 핵심 원칙

### 5.1 표준은 하나, 채널은 여럿

```
어디서 말하든 (텔레그램, 디스코드, 웹)
→ 같은 코어 엔진
→ 같은 블록이 실행됨
→ 같은 품질이 보장됨
```

### 5.2 오케스트레이션은 보이지 않는다

사용자에게 파이프라인, DAG, 모델 라우팅을 노출하지 않는다.
이 모든 것은 내부에서 자동으로 처리된다.

### 5.3 네이티브를 활용한다

Claude Code가 이미 제공하는 기능(Remote Control, Channels, 세션 관리, 보안)은
직접 구현하지 않고 네이티브로 활용한다.

### 5.4 만들 것만 만든다

Vibe Flow가 만드는 것:
- 블록 정의/저장/버전 관리
- 블록 매칭 엔진 (trigger_phrases 퍼지 매칭 + IntentClassifier 폴백)
- 실행 하네스 (컨텍스트 주입, 품질 게이트, 재시도)
- Creator 웹 UI

Vibe Flow가 만들지 않는 것:
- 채팅 봇 (Claude Code Channels 사용)
- 웹/모바일 접근 (Claude Code Remote Control 사용)
- 인증/보안 (Claude Code allowlist 사용)
- AI 실행 엔진 (Claude Code CLI 사용)
- 벡터 DB / 임베딩 인프라 (수십 개 블록에는 과잉, 필요 시 추후 도입)

### 5.5 블록의 범위

> 비판적 검토를 통해 블록의 적용 범위를 명확히 정의했다.

```
블록 대상 (팀당 5-15개의 핵심 반복 워크플로우):
  - DB 스키마 설계, API 설계, 코드 리뷰, 보안 점검
  - 품질 게이트(자동 검증 + 재시도)가 가치를 발휘하는 구조화된 산출물

블록 비대상 (일반 Claude Code로 처리):
  - 디버깅, 탐색, 리팩토링, 1회성 질문
  - 비구조적이고 맥락 의존적인 작업

블록의 유일한 고유 가치 = 품질 게이트
  - 프롬프트 표준화 → CLAUDE.md로 80% 해결 가능
  - 팀 컨벤션 → CLAUDE.md로 해결 가능
  - 품질 게이트 → CLAUDE.md로 불가능. 블록만의 고유 영역
```

## 6. 경쟁 포지셔닝

```
            개인용              팀용
           ─────────────────────────────
직접 코딩  │ Cursor            │ GitHub Copilot
           │ Claude Code       │ Enterprise
           │                   │
대화형     │ Lovable, Bolt     │ ← Vibe Flow
           │ v0, Replit Agent  │   (여기가 비어있음)
           ─────────────────────────────
```

Lovable/Bolt은 개인이 빠르게 프로토타입하는 도구.
Vibe Flow는 **팀이 일관된 품질로 AI를 활용하는 표준화 플랫폼**.

---

## 7. 한 줄 정의

> **Vibe Flow: 바이브코딩의 재현 불가능성을 고정 파이프라인으로 해결하고,
> 팀원은 자기만의 블록으로 자유롭게 작업하되 같은 품질을 보장받는 플랫폼.**
